Quality OS — delivery and operating guide

A connected, local single-user engineering workbench extending the recovered DQOS and BAPSI workflows. This delivery supplies working calculations, shared case records, editable evidence registers, reports, a verification workbook and reproducible source. It is a scoped release; it is not yet the full QualEngine feature inventory or an enterprise QMS.

1. Open and retain your work

  1. Extract all of the Offline ZIP to a short local folder. Open START_HERE.html, or download and open the single-file Barkati_Quality_OS_Offline.html.
  2. Use a browser capable of executing local HTML. Calculations, method notes, case edits, charts and exports do not need internet. The single file also embeds the workbook and guides as downloadable resources.
  3. Start with the clearly marked synthetic demonstration. Export your current case before using New blank case or Load demonstration.
  4. Use Export case after each working session. JSON is the portable record, including measurement inputs, linked registers and saved studies. Import validates the case before replacing the working state.
  5. Browser local storage is a convenience, not a backup. It may be unavailable for file URLs, private browsing or mobile file previews. The app reports storage failures; use JSON export.

Mobile layout is responsive, but no physical iOS/Android device was tested. Some mobile file previewers do not run JavaScript. Open the extracted HTML in a compatible browser, or use the hosted application. The hosted page is not advertised as an installed offline PWA.

2. Demonstrate a connected case in 15 minutes

  1. Overview: identify the case, characteristic, revision, synthetic flag and review status. All numerical examples are synthetic; none is a claimed customer result.
  2. Case & data: inspect 30 subgroups of five readings. The first 25 estimate the baseline. The final five contain a deliberate shift. Specification limits are 9.98–10.02 mm.
  3. SPC: review both location and dispersion charts, five mean signals, zero out-of-spec readings and the HOLD / REVIEW decision. High capability indices do not remove control-chart signals.
  4. Measurement studies: run the crossed GR&R demonstration and select Add to evidence. Inputs and results are retained; the reviewer remains blank until an actual review.
  5. SPC → Create investigation: carry the signal snapshot into evidence and problem definition. No cause is automatically declared.
  6. Investigation & 8D: enter team/problem boundaries; document stock exposure at all five locations; link occurrence, escape and systemic hypotheses to evidence and falsification tests. Inspect blocked gates.
  7. Connected FMEA: inspect the Design → Process → Equipment links and the linked Control Plan. Request review through the risk chain; ratings do not change automatically.
  8. APQP / PPAP and Audit: inspect required deliverables, owners, evidence and review fields. A status label alone does not establish customer acceptance.
  9. Report / PDF: open the report, then Print / save PDF or Download HTML. The HTML preserves navigation and readable tables. PDF printing depends on the browser and is not a fillable form or dynamic app.
  10. Export / restore: save JSON, reload the application, import JSON and compare case ID, measurements and results.

fixtures/completed-synthetic-8D.json provides a complete fictional evidence chain for studying gate logic. Its fictional reviewer names and references do not represent real approvals.

4. Verification workbook

Open Quality_OS_Verification_Workbook.xlsx. Teal cells are editable inputs. Measurements contains a fixed 30-row, n=5 Xbar–R study, baseline count and specifications. Study results recomputes within/overall estimates, centered capability indices, both chart signal counts and out-of-spec readings. Bias study supports up to 30 readings, a reference, tolerance and allocation fraction. Actions separates implementation verification from effectiveness validation. Capability register describes the release scope.

The workbook is a cross-check and action companion, not a synchronized Excel add-in. It was recalculated and rendered in the artifact engine, including a dispersion-signal mutation; it was not opened in desktop Excel in this session. Changing its fixed layout requires formula review.

5. GitHub and Netlify deployment

  1. Extract the GitHub_Netlify ZIP. Keep its folder structure. Upload the contents to a new private GitHub repository; do not upload only the ZIP.
  2. Install Node.js 20 or newer. No runtime npm dependencies or API keys are required. Run the commands below from the extracted root.
  3. GitHub Actions runs engine/workflow tests, mutation checks, build and offline smoke checks. Inspect the workflow result before releasing.
  4. In Netlify, import the repository. Build command: npm run build. Publish directory: dist. The supplied netlify.toml holds these settings.
  5. Alternatively, run the build and drag the dist folder into Netlify manual deployment. Upload built assets, not src alone.
  6. Open the deployed app, run the synthetic demonstration, export/import JSON and check workbook/guide downloads. Configure access with the hosting provider before handling confidential cases.

6. Data contracts and controlled integration

  • Measurement CSV: one rational subgroup per row, no header, decimal point, comma/semicolon/tab separators. Blank numeric cells, text, non-finite numbers and incomplete rows are rejected. Entirely empty lines are skipped.
  • Case JSON: schema barkati.quality.case.1; records link by stable IDs. src/model.js validates structure, values and duplicates. Save originals before migration.
  • Legacy DQOS: import dqos.case.1.0 measurement exports. Full groups are mandatory; old approval booleans are deliberately not imported. Other old records require reviewed mapping.
  • AP lookup: use the in-app import example for the exact contract; provide source, revision and valid S/O/D tuples mapped to H/M/L. The example is a formatting illustration, not a sanctioned AP table.
  • Current portfolios: add a product entry linking to this release and its evidence, under Digital Quality OS. Keep all approved photographs, Kaizen evidence, NIDEC/AVO milestones and existing services. Do not replace the master portfolio with this application or imply invented customer outcomes. Portfolios are not changed by this release.
  • Future adapters: map tenant/customer/product/process/characteristic IDs, units, time zones, sampling order, revision and approval state before enabling live data exchange. Require round-trip and reconciliation tests on customer-approved samples.

7. Architecture and data handling

engine.js is a pure calculation/governance module; model.js defines the shared case; content.js holds methods and navigation; app.js renders the UI. The build produces static assets and a single-file offline application. No telemetry, remote fonts, CDN or inference endpoint is used by the runtime.

This is a single-user local workbench. Storage is not encrypted by the app. Anyone with access to the browser profile or exported files may read them. The activity log is editable JSON and is not tamper-proof. Clear the relevant browser site data and delete exports to remove retained cases. Hosted authentication, tenant isolation, retention enforcement, server audit records and controlled electronic approvals belong to the backend increment. Do not describe the current release as a validated multi-user enterprise QMS.

9. Release and pilot acceptance

  1. Numerical reference checks and malformed-input tests pass.
  2. JSON export/import preserves calculations and records; invalid imports fail visibly.
  3. Changing baseline/measurement evidence invalidates closure; status-only assertions do not pass evidence gates.
  4. Offline HTML contains every runtime asset and embedded companion downloads.
  5. Every ZIP passes CRC and full extraction with file hashes matching its manifest.
  6. Customer pilot compares its approved datasets and workflows with the current controlled method. A qualified reviewer resolves differences before operational release.

See qa/QA_Report.json in the source bundle for the exact checks and untested environments. Test counts are evidence of selected verification, not a promise of zero defects.
